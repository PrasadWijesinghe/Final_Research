# Components

A plain-language guide to every part of the system. Each component has a `README.md` in its
own folder, written from `docs/templates/COMPONENT_README.md`. Start here to understand
what exists and how far along it is.

| Component | What it does | Guide | Status |
|---|---|---|---|
| Contracts | The messages services send each other | `shared/contracts/README.md` | Working (v1.1) |
| Database layer | Describes the raw and platform tables and creates them with Alembic migrations | `shared/db/README.md` | Working (P0.6) |
| GitHub client | Reads the GitHub REST API and raw files with rate-limit waits, retries and date-window splitting; downloads job logs and run-attempt log archives, with a size limit (`max_bytes`, D41), and reads the quota from the API's answer even after a redirect (D41) | `shared/github/README.md` | Working (P1.1, D41 size limit and redirect quota headers) |
| Collector | Loads and validates each member's repo list, decides which workflow files are relevant (rules for Test and Build), backfills the last 90 days of runs, jobs, commits and config files in two passes (`backfill --logs failed`, then `fill-logs`, optionally `--passing failed-runs`, which fetches passing-job logs only for runs with a failure; `fill-logs` fetches each run attempt's logs as one zip by default, with `--no-archive` for one request per job, D41), sets aside runs GitHub keeps failing on (5xx) and retries them later, keeps everything up to date with a daily sync, reports what is stored, pending logs, skipped runs, gaps and the rate limit (`status`), prints a read-only data-quality report per repo with the problems to look at (`report --member <m> [--out FILE]`, needs only `DATABASE_URL`), and bundles the database and files into one archive that can be imported elsewhere (`make export-data`, `make import-data`) | `services/collector/README.md` | Working (P1.2, P1.5 backfill with D38, D39 and D40, D41 archive mode in `fill-logs`, P1.6 daily and status, P1.7 export and import, P1.8.md`). The SQL integration tests (export and import, backfill, daily and status) run in `make check` against the throwaway `pipelineiq_collector_test` database. They skip, not pass, if Postgres is down |
| Repository helper scripts | Adds selected Dependency candidate groups to the repo config without replacing existing settings; checks each member's repos on GitHub for runs, failure rate, re-run share, retention, workflows and licence match | `scripts/README.md` | Working (P1.3, P4.14) |
| Build screen script | Checks the Build repos with a real token: 90-day runs and failures of build workflows, share of build-type failed steps, estimated backfill cost, and a keep / too quiet / expensive suggestion | `scripts/README.md` (section "Build screen") | Written and tested on canned answers (B2); not yet run against GitHub |
| Sanitiser | Removes secrets (tokens, keys, passwords, auth headers) from CI logs and counts the removals; hashes author logins with a team salt | `shared/sanitise/README.md` | Working (P1.4) |
| Features service | Gives each changed file its tags (such as `test`, `lockfile`, `workflow`) from `config/file_tags.yaml` and drops patches that are too big to store. Builds the `CommitContext` for a live commit (GitHub API), a stored CI run (replay, from the raw tables) or an unpushed commit (pre-push payload), with one shared assembly step, so the three agree | `services/features/README.md` | Working (P2.2 file tagger, P2.3 CommitContext builders). The SQL replay test (integration) has never been run. The replay command that calls the replay builder is in `services/api` (P2.8) |
| LLM gateway | The only door to the language model. Takes a request from an expert, returns an answer checked against the requested JSON Schema (one retry if invalid), caches identical requests, enforces a monthly spending cap per expert and logs every paid or cached call to `platform.llm_calls`. Only the mock provider exists (decision O5 open) | `services/llm_gateway/README.md` | Working with the mock provider only (P2.4). The SQL log test (integration) has never been run |
| Embeddings and hybrid search | Cleans CI logs (timestamps, hashes, ids and paths become placeholders), turns text into 384 numbers with the granite model (an optional extra, loaded on first use) or a fake embedder for tests, and gives each expert a pgvector table that answers keyword plus meaning searches, merged with reciprocal rank fusion | `shared/embeddings/README.md` | Working (P2.5). The real model is never loaded in tests. The two SQL tests (integration) have never been run |
| Backend API | The one front door on port 8000. Pre-push `/predict` (API key in, fan-out to the four experts in parallel with a 10 s budget and `X-Deadline-Ms`, four results back, contracts saved to `platform`), worker `/diagnoses`, dashboard `/reviews` (forwarded to the expert), `/commits/{sha}/risks`, `/runs`, `/failures/{id}`, `/health`, and API key issue and revoke (admin token). `POST /webhooks/github` (P3.1): signed GitHub App events drive the live predict flow, raw storage with `source="app"` and failure routing; GitHub sign-in still returns 501. Router: scores a failed job per expert from `config/router_rules.yaml`, sends it to the top one or two experts, saves the `RoutedFailure` and queues one job per expert on `diagnose:<expert>`. Unknown failures are logged only | `services/api/README.md` | Working for pre-push, history, reviews and keys (P2.6). Router written with 41 unit tests on fakeredis (P2.7), called by the replay CLI (P2.8); P3.1 will call it too; the test run is not recorded in the guide. Read endpoints and `/diagnoses` are unauthenticated until P3.1. Dockerfile and `e2e` compose profile plus an end-to-end test (`make e2e`, P2.9) written but not built or run. The SQL tests (integration) are not yet recorded as run; they use a throwaway `<db>_api_test` database |
| Replay CLI | Replays stored CI runs in a date window (`--member`, `--from`, `--to`, `--data-dir`) through the experts and the router. Rebuilds each commit from the raw tables, stores predictions with `is_replay` and failures with `replay`, and queues routed failures on the live expert queues. Never calls GitHub | `services/api/README.md` (section "Replay CLI (P2.8)") | Written (P2.8). Unit tests written (6) but not run while the guide was written. Not run end to end. The SQL source test (integration) has never been run. Architecture doc says the CLI is in `services/features`; the code is in `services/api` (flagged) |
| Expert template | The starting point for all four experts: a stub API (`/predict`, `/review`, `/health`), a stub diagnose worker, a Dockerfile and tests. Copied, then renamed, for each expert | `experts/_template/README.md` | Stub (P2.1). Tests pass; Docker not built or run |
| Dependency expert (stub) | Stub of the Dependency and Runtime expert (port 8101, queue `diagnose:dependency`); also contains an experimental dataset, feature, audit, baseline evaluation, model and heuristic log-labeling prototype with bounded candidate batches, random control sampling, and reviewed-label consolidation, not connected to `/predict` | `experts/dependency/README.md` | Stub + experimental prototype (P2.1, P4.13–P4.21). Tests pass; Docker not built or run |
| Build expert | Build and Code Quality expert (port 8102, queue `diagnose:build`), owner Member 2. Dataset pipeline: parses tsc, ESLint, Prettier and bundler output in CI logs, labels failed jobs with named rules (`FailureLabel`s), rebuilds each commit by replay, computes 99 pre-run features in four groups with no look-ahead, mines fix candidates, and writes a frozen `data/datasets/build/vN/` (`build-dataset`). Trains and evaluates LightGBM against two baselines with temporal and leave-one-repo-out testing, calibration, thresholds, ablation and SHAP, and exports a model bundle with a report (`build-train`); manual label check helper (`build-label-check`). `/predict` serves the model with sub-risks and SHAP risk factors (stub when no model is configured); the worker diagnoses failed jobs with tool, locations, evidence and similar past fixes from `build.kb_cases` (`build-kb`), or answers misrouted; `build-demo` writes real examples; the dashboard's Build Expert tab (`services/dashboard/src/build/`) shows predictions and diagnoses through `/predict`, `/diagnose`, `/model` and `/examples` | `experts/build/README.md`, design `docs/experts/build.md` | B1–B12 working: model `build/m4` trained on 3 of 11 real repos (test F1 0.567 against 0.385 for the best baseline); code-embedding variant, KB review and the two-person label check pending. `/predict` serves the model when `BUILD_MODEL_DIR` is set (stub otherwise); Docker not built or run |
| Test expert (stub) | Stub of the Test and App Behaviour expert (port 8103, queue `diagnose:test`). Its `/predict` is per test job. Also the log parsers (P4.1): read a failed Jest, Mocha or Vitest log into failing tests, per-test results and stack frames; any other log is `other`. Owner Member 3 | `experts/testing/README.md`; parsers: `experts/testing/src/testing_expert/parsing/README.md` | Stub (P2.1). Log parsers working (P4.1), not yet used by `/predict` (P4.2, P4.3 next). Tests pass; Docker not built or run |
| Infra expert | Trained Infra research model on port 8104, plus a local dashboard that connects one GitHub repository branch and predicts newly observed remote revisions | `experts/infra/LIVE_PREDICTION.md` | Local polling monitor and prediction UI implemented; nested repository validation still shows poor recall; dataset audit and human-review workflow in `experts/infra/research/DATASET_REPAIR_REPORT.md`; RAG/LLM and GitHub App remain separate work |
| Pre-push hook | A Node 22 script run by `git push`. Sends the unpushed diff and config files to the API's `/predict` with your API key (env or `~/.pipelineiq`), prints the risks, asks "Push anyway?" only at a terminal, and always lets the push go on when anything fails or 10 s pass. Installer writes `.git/hooks/pre-push` | `tools/pre-push-hook/README.md` | Working (P3.4). Tests use real temp git repos and a fake HTTP server; run in `make check` and CI |
