# Components

A plain-language guide to every part of the system. Each component has a `README.md` in its
own folder, written from `docs/templates/COMPONENT_README.md`. Start here to understand
what exists and how far along it is.

Router: scores a failed job per expert from `config/router_rules.yaml`, sends it to the top one or two experts, saves the `RoutedFailure` and queues one job per expert on `diagnose:<expert>`. Unknown failures are logged only | `services/api/README.md` | Working for pre-push, history, reviews, keys (P2.6), sign-in (P3.5), webhooks (P3.1) and PR checks (P3.3, GitHub mocked in tests). The SQL tests (integration) are not yet recorded as run; they use a throwaway `<db>_api_test` database |

Never calls GitHub | `services/api/README.md` (section "Replay CLI (P2.8)") | Written (P2.8). Unit tests written (6) but not run while the guide was written. Not run end to end. | Build expert | Build and Code Quality expert (port 8102, queue `diagnose:build`), owner Member 2. Dataset pipeline: parses tsc, ESLint, Prettier and bundler output in CI logs, labels failed jobs with named rules (`FailureLabel`s), rebuilds each commit by replay, computes 99 pre-run features in four groups with no look-ahead, mines fix candidates, and writes a frozen `data/datasets/build/vN/` (`build-dataset`). Trains and evaluates LightGBM against two baselines with temporal and leave-one-repo-out testing, calibration, thresholds, ablation and SHAP, and exports a model bundle with a report (`build-train`); manual label check helper (`build-label-check`). `/predict` serves the model with sub-risks and SHAP risk factors (stub when no model is configured); the worker diagnoses failed jobs with tool, locations, evidence and similar past fixes from `build.kb_cases` (`build-kb`), or answers misrouted; `build-demo` writes real examples; the dashboard's Build Expert tab (`services/dashboard/src/build/`) shows predictions and diagnoses through `/predict`, `/diagnose`, `/model` and `/examples` | `experts/build/README.md`, design `docs/experts/build.md` | B1–B12 working: model `build/m4` trained on 3 of 11 real repos (test F1 0.567 against 0.385 for the best baseline); code-embedding variant, KB review and the two-person label check pending. `/predict` serves the model when `BUILD_MODEL_DIR` is set (stub otherwise); Docker not built or run |
| Test expert | Test and App Behaviour expert (port 8103, queue `diagnose:test`). Its `/predict` is per test job and serves a trained LightGBM model, v4 (`lightgbm-v4`): one booster for genuine failures and one for flaky ones, beta-calibrated, loaded from `models/testing/v4`, with the stub as fallback. Features: change size, source/test links, history, tree-sitter counts of risky test changes (`tw_*`), history by runner OS (`h_os_*`). Per-test history (`ht_*`) is built, but v4 does not use it. Reasons are SHAP-style contributions (P4.8, `explain.py`). Triage of failed test jobs (P4.9, `triage/`): genuine, flaky or unclear with a confidence floor and `suggest_rerun` only for a confident flaky verdict, from stack-vs-diff overlap, error type, test history, same-commit evidence and the pre-run risk. Knowledge base (P4.10, `kb/`): 1,233 mined cases (602 genuine, 631 flaky) with rule-based tags, granite embeddings and hybrid full-text + vector retrieval (RRF, top 5, no future leakage, no self-retrieval, licence filter) feeding `Diagnosis.retrieved_cases` (one case per fix commit in the diagnosis path); CLI `python -m testing_expert.kb build|search|eval`. Diagnosis narrative (P4.11, `rag/`, `config/test_diagnosis.yaml`): prompt `rag/prompts/diagnose.md` (git-hash `prompt_version`), call to the LLM gateway with a JSON schema, citations limited to retrieved case ids, `status="misrouted"` for logs with no test failure, and a no-LLM template for every fallback and for the mock provider. Reports in `experts/testing/reports/` (`kb_v1`, `v2_vs_v1`, `v3_vs_v2`, `v4_vs_v3`, `v5_vs_v4`, `v6_vs_v4`, `triage_v1`). Also the log parsers (P4.1), results extraction (P4.2), labels (P4.3), datasets v1 to v4 (P4.5) and model training (P4.6, P4.7). Owner Member 3 | `experts/testing/README.md`; parsers: `experts/testing/src/testing_expert/parsing/README.md` | Knowledge base built (P4.10): tags and fixes are rules, not human-checked, and the failure text barely predicts the fix category (`reports/kb_v1.md`); Docker worker retrieves by full text only (no torch in the image). Only the mock LLM provider exists, so the diagnosis text today comes from the template; the real-model path is tested with a fake gateway only (a provider class, `LLM_PROVIDER` and `LLM_API_KEY` are still needed). Model v4 served (P4.7, P4.12 partial); `testing-api` rebuilt and `/health` shows `lightgbm-v4`. The diagnosis worker now triages (bundle `models/testing/triage/v1`, 83% coverage, 4% false-flaky on the time-based test, weak on unseen repos; narrative text now from `rag/`, P4.11). v5 (per-test history) and v6 ("still failing" rule, calibration-chosen threshold) were not better and are candidates in `models/testing_candidates/`, not served; serving can already read a v6 bundle (`rule.json`) and skips the slow per-test history query for bundles that do not use it. | Infra expert | Trained Infra research model on port 8104, plus a local dashboard that connects one GitHub repository branch and predicts newly observed remote revisions | `experts/infra/LIVE_PREDICTION.md` | Local polling monitor and prediction UI implemented; nested repository validation still shows poor recall; dataset audit and human-review workflow in `experts/infra/research/DATASET_REPAIR_REPORT.md`; RAG/LLM and GitHub App remain separate work |
| Pre-push hook | A Node 22 script run by `git push`. Sends the unpushed diff and config files to the API's `/predict` with your API key (env or `~/.pipelineiq/config`), prints the risks, and asks "Push anyway?" only at a terminal. With no terminal (GUI push buttons, AI agents) it shows a desktop notification with a link to the commit in the dashboard and lets the push go on. Opt-in `block_when_no_tty=true` in `~/.pipelineiq/config` stops the push when a risk was flagged (off by default). Always lets the push go on when anything fails or 10 s pass. Settings in `~/.pipelineiq/config`: `api_key`, `api_url`, `dashboard_url`, `block_when_no_tty`. Installer writes `.git/hooks/pre-push` | `tools/pre-push-hook/README.md` | Working (P3.4). No-terminal notification and opt-in block added. Tests use real temp git repos and a fake HTTP server, and cover notifications and the block; run in `make check` and CI |
